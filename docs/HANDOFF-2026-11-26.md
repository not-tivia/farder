## Encrypted channel

**FIXED (a0735f97): an encrypted channel used to break after the first exchange.** Cause, from the server's event log: right
after the owner adds a friend, BOTH apps refresh their keys on their next send. Two bugs made that fatal:
1. Adding a member rebuilt the owner's channel record from defaults (`..Default::default()`), wiping its refresh history and
   cursor, so the owner thought it had never committed and refreshed on its very next send, racing the friend's first refresh.
2. `rekey_channel` merged the refresh BEFORE the server answered. The loser of the race sat alone on a private epoch, skipped
   the winner's commit as an "old repeat" (`processed: 0`), and nothing opened either way.
Fix: the refresh is staged (`self_update_staged`) and only applied on acceptance; any refusal discards it
(`E2eeError::RekeyRefused`, not a divergence); a lost answer stays staged and `settle_staged_refresh` decides from the log (steward
and send path). Adding a member updates the record and records the own commit. The steward now reports `group.epoch()`.
Pinned by `tests/e2ee_lifecycle.rs` `two_key_refreshes_at_once_do_not_fork_the_channel` (red before, green after) plus farder-mls
unit tests of OpenMLS's staged-commit behaviour. `ubuntu-suite.sh e2ee`: 7/7, three runs in a row. Channels that already forked are
NOT healed (owner reset is the way out). Still merge-before-submit: add and remove commits (same shape, rarer; not fixed).


Was "UNVERIFIED: GUI path unseen". The new suite found three real bugs, all fixed and re-run:

1. **The friend never got the first message** in a new encrypted channel: B only published its key package when it OPENED the channel,
   so A's first message was sealed before B was in the group. Now a member whose app is ONLINE AND SHOWING THAT SERVER publishes as
   soon as the channel appears (`server:channel_created_v2` in `useServerEvents.ts`). Offline members, members looking at another
   server and late joiners still publish on first open, so their first message can still be "sent before you could read".
   `publish_own_key_package` now refuses (returns `skipped`) over a confirmed or poisoned state, checked under the device-chain lock:
   before, only the frontend guarded it, and a Welcome could land between its `process` and `publish` calls and be reset.
2. **A message that arrived before the reader's Welcome was cached as "couldn't decrypt" forever** (reason "no MLS group for
   channel"; nothing had been opened). `decrypt_sealed_message` now answers `not_ready`; `useSealedDecrypt` does not cache it and
   opens the row again when the channel's `mlsStates` changes.
3. **A message sealed before you were added looked like tampering** (red "couldn't decrypt" + "1 message could not be verified").
   `farder-mls` now reads the header epoch and says `BEFORE_JOINED`; the app shows "Sent before you could read this channel", not red,
   not counted. Unit test in `farder-mls` (also checks a tampered current-epoch message is NOT relabelled). CAVEAT: the test is
   "older than the group's CURRENT epoch", not "older than when this device joined" (the join epoch is not stored); a long-time
   member who lost local history would see old messages with this calm label rather than the warning.

What the suite covers: two online apps, text only. NOT run: relaunch and reading history, sealed attachments, a late joiner, three
or more members. The phone-width list view hides the chat panel, so the takeover/saved-copy banners do not show there (the
takeover toast still does).

## Appendix: canary issue text (file it once the GitHub agent is live)

Title: Deleting a channel that does not exist should be refused and not use brake budget

**Problem.** `ServerRequest::DeleteChannel` for a channel id that does not exist answers success (see the `DeleteChannel` arm in `crates/farder-server/src/handlers.rs`). Because the bulk-damage brake (`crates/farder-server/src/brake.rs`, `docs/modules/brake.md`) counts every successful destructive change, a client that retries a stale delete uses up the owner's budget (5 per 10 minutes) for nothing.

**Wanted.**
1. Deleting a channel id that does not exist returns `ServerResponse::Error` with a plain reason (e.g. "that channel no longer exists").
2. That refusal does NOT use brake budget.
3. Deleting a real channel works exactly as before (including the audit log row and the broadcast).

**Tests (headless, `cargo test -p farder-server`).** Add unit tests next to the existing brake tests in `handlers.rs`:
- deleting a missing id returns `Error` and the reason says the channel does not exist;
- after 5 deletes of missing ids, the owner can still delete 5 real channels before the brake says "slow down".

Prove the tests pin the fix: they must fail with the old behaviour.

**Out of scope.** No client/UI changes. No protocol enum changes.

**Done means.** `cargo test -p farder-server` passes, `python3 scripts/seam_audit.py`, `scripts/reachability_audit.py` and `scripts/doc_audit.py` pass, and `docs/modules/brake.md` mentions that a missing channel is refused without using budget.
